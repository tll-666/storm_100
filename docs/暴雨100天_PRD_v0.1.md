## 1. PRD是什么

PRD是 Product Requirements Document 的缩写，中文通常叫“产品需求文档”。它用于说明：

- 我们要做一款什么产品；
- 它解决什么体验目标；
- 面向什么玩家；
- 必须包含哪些功能；
- 当前版本做到哪里、哪些内容暂时不做；
- 做到什么程度才算完成。

PRD主要回答“做什么、为什么做、做到什么程度”，不负责写出所有剧情台词，也不等同于代码说明。游戏项目还可能有更细的游戏设计文档（GDD）、剧情文档、数值表和美术规范。由于本项目目前由小规模团队或个人推进，本PRD同时承担总体游戏设计纲要的作用，后续再把事件、数值、剧情和美术拆成独立文档。

## 2. 产品概述

### 2.1 一句话介绍

玩家与伴侣、两个孩子和一名老人组成五口之家，在持续一百天的异常暴雨中留守自己的两层住宅，通过观察环境、判断信息、管理物资、维护家庭关系和应对房屋退化，设法让一家人共同活到灾难结束。

### 2.2 核心差异

本作不是只在菜单中选择“吃什么、派谁出去”，也不是大型开放世界求生游戏。玩家能够在自己的家中移动，进入不同房间，与家人、家具、容器、车辆和房屋设施直接互动。随着灾难发展，同一栋房屋会不断改变：停电、停水、漏水、潮湿、车库积水、一楼被淹，最终生活空间被压缩到二楼和阳台。

### 2.3 主题

本作讲述的不是一次瞬间爆炸，而是持续灾难如何慢慢改变普通家庭、住宅和社区。真正的压力来自有限信息下的判断：玩家经常无法确定天气预报、邻居消息或眼前迹象是否可靠，只能提前准备并在数天后承担结果。

## 3. 产品目标

### 3.1 玩家体验目标

1. 让玩家感到“这确实是我熟悉的家”，并逐渐看到它从住宅变成避难所。
2. 让购物、整理、修补、和外出都成为对未来风险的判断，而不是单纯收集更多物品。
3. 让家庭成员有实际作用、情绪和意见，但不把游戏变成复杂的人际数值模拟器。
4. 让玩家能够从环境和对话中预判事件；做对时产生“我早就注意到了”的满足感，做错时也能理解原因。
5. 让选择产生轻微、延迟、可回收的变化，保持剧情丰富度，同时避免分支无限膨胀。

### 3.2 当前开发目标

先完成30—50分钟的纵向切片，从“暴雨前第3天”推进到“暴雨第3天夜间结算”，验证房屋探索、购物、接人、天气升级、家庭结算和车库渗水是否能够形成完整体验。纵向切片通过测试后，再扩展到更长的生存阶段。

### 3.3 非目标

- 当前不制作完整100天的全部事件。
- 不制作无缝大城市或可以进入每栋建筑的开放世界。
- 不为每个日常行为建立独立进度条，例如洗衣、排便和洗澡不做成重复操作小游戏。
- 不让每一次选择都发展成永久分离的主线。
- 不在灰盒阶段制作大量无功能家具和最终美术。
- 不同时追求Steam完整版和微信小游戏完整版；微信端仅考虑后期轻量版本。

## 4. 目标玩家与平台

### 4.1 目标玩家

- 喜欢剧情选择、灾难题材和资源管理的玩家；
- 喜欢从细节、对话和环境变化中推理后果的玩家；
- 能接受节奏偏慢、压力逐步累积，而不是持续战斗的玩家；
- 喜欢多次游玩，观察不同准备和决定所产生差异的玩家。

### 4.2 发布方向

| 平台 | 定位 |
| --- | --- |
| Steam / Windows | 完整单机正式版，当前所有系统首先按此目标设计 |
| B站 | 开发日志、预告片、演示视频、测试玩家招募和社区反馈 |
| Web | 短流程试玩版，降低体验门槛 |
| 微信小游戏 | 后期单独评估的轻量衍生版，需要缩减场景、资源和平台功能 |

## 5. 核心设计思想

### 5.1 核心循环

> 观察 → 获得不完整信息 → 预测风险 → 作出决定 → 等待变化 → 承担结果 → 再次观察

玩家不应该主要输给无法预知的随机惩罚，而应该输在误判、忽视迹象、资源不足或接受了某种风险。随机性可以改变事件出现方式，但不能替代因果。

### 5.2 预测原则

- 重要事件尽量提前提供至少一个线索。
- 线索可以来自收音机、天气预报、窗外水位、风声、社区消息、家人对话和房屋状态。
- 信息不保证完全可靠，不把正确答案直接写给玩家。
- 同一风险最好存在两种以上应对方式，不只允许购买某个唯一道具。
- 玩家没有及时行动，也应被系统视为一种选择。

### 5.3 留白原则

- 不解释所有结果，允许玩家自己判断邻居是否撒谎、某次故障是否由此前决定造成。
- 不立即公布所有隐藏数值和判定过程，以环境反馈、人物反应和资源变化呈现后果。
- 部分选择只改变台词、信任或后续事件权重，不必每次都改变主线。
- 灾难之外仍保留普通生活：孩子想吃零食、老人摆弄收音机、伴侣担心家务。这些细节让严重事件更有重量。

### 5.4 事件原则

1. 事件首先提出一个问题，而不是考玩家唯一正确答案。
2. 选项必须有可以理解的利益和代价。
3. 后果允许延迟数小时或数天出现。
4. 重大事件应尽量在场景中发生，例如水进入车库、灯光熄灭、人物移动，而不是只弹出文字框。
5. NPC主要使用“信任、承诺和状态标签”，不展示传统好感度进度条。
6. 地图不需要很大，但同一地点必须随着日期、天气和家庭行动持续变化。

## 6. 世界与场景范围

### 6.1 世界范围

主要舞台是一处城市边缘的独栋住宅社区。完整版本以“一条住宅街、一个小社区”为主要外部范围，目标约12名重要NPC。只有少数住宅和公共地点可以进入，其余房屋通过外观、对话和事件参与世界变化；可进入的邻居住宅优先复用房屋模板，避免每栋房子完全独立制作。

### 6.2 玩家住宅

| 区域 | 房间或地点 | 主要作用 |
| --- | --- | --- |
| 一楼外部 | 住宅街、前院、车道 | 观察天气、水位、邻居和外部事件 |
| 一楼 | 车库 | 汽车、工具、外出准备；地势最低，最早积水 |
| 一楼 | 客厅 / 餐厅 | 家庭事件、讨论和每日安排中心 |
| 一楼 | 厨房 / 食品柜 | 烹饪、冰箱、主食和饮水储存 |
| 一楼 | 厕所 / 洗衣区 | 卫生用品、清洁用品、上下水状态 |
| 一楼 | 老人卧室 | 老人休息和专属事件；后期撤离一楼时产生压力 |
| 一楼 | 楼梯间、玄关、过道、配电箱 | 楼层交通、进出住宅、电力检查 |
| 二楼 | 主卧 | 玩家与伴侣休息、结束当天 |
| 二楼 | 大孩子房 | 电子设备、学习和大孩子事件 |
| 二楼 | 小孩子房 | 玩具、绘本和小孩子情绪事件 |
| 二楼 | 厕所 | 与一楼共用管线，反映水压和排污问题 |
| 二楼 | 家庭活动区、储物角 | 一楼被淹后的临时生活和物资转移区 |
| 二楼 | 公共阳台 | 观察、接雨水、求救、投递和后期外部互动 |

家具只有在承担储存物资、执行行动、显示房屋状态、触发事件或提供剧情信息时才设置互动。纯装饰物作为背景绘制，不额外增加碰撞和交互成本。

### 6.3 房屋长期变化

房屋需要成为贯穿100天的“第二主角”：

1. 灾前：普通住宅，生活物资不足但功能正常。
2. 初期：停电、低水压、车库渗水、阳台排水压力。
3. 中期：潮湿、霉变、房间漏水、部分设施失效、物资向高处转移。
4. 后期：车库和一楼逐步被淹，老人房等区域失去使用价值。
5. 末期：家庭主要生活在二楼，阳台承担观察、求救和外部交换功能。

## 7. 五人家庭

角色不采用复杂职业树。每人需要一个明显长处、一个明显短处和一类专属事件倾向。

| 角色 | 当前功能定位 | 长处方向 | 短处方向 | 事件倾向 |
| --- | --- | --- | --- | --- |
| 玩家 | 执行行动并代表家庭作决定 | 行动自由、可使用车辆和工具 | 时间与携带能力有限 | 外出、维修、分配和关键决定 |
| 伴侣 | 家庭秩序与物资管理 | 整理、照料、发现生活必需品短缺 | 压力累积后容易与玩家产生意见冲突 | 家务分配、物资清单、家庭争执 |
| 大孩子 | 信息和电子设备 | 使用手机、充电设备和社区信息 | 容易质疑管束或自行冒险 | 学校、通信、网络消息、外出冲动 |
| 小孩子 | 家庭情绪与脆弱需求 | 能提升家庭的生活感和凝聚力 | 恐惧、无聊和环境变化影响更明显 | 玩具、食物偏好、雷雨恐惧、意外发现 |
| 老人 | 经验与风险提醒 | 观察生活细节、重视存货和收音机 | 体力和健康恢复能力较弱 | 旧经验、传统办法、身体不适、撤离一楼 |

以上是功能定位，不是完整人物背景。姓名、年龄、职业和更具体的性格需要在人物设计文档中另行确定。

## 8. 时间与流程

### 8.1 时间规则

- 普通移动、查看家具、打开容器和普通对话不消耗时间。
- 购物、外出、维修、整理、陪伴和睡觉等重要行动推进时间。
- 不建立需要频繁操作的“上午—中午—下午—晚上”回合表，但界面显示当前时段，重要行动改变时段。
- 每天通过睡觉或明确的结束行动进入结算。
- 日期切换画面必须等待玩家点击“进入新的一天”或按回车，不能自动闪过。

### 8.2 灾前三次购物

| 次数 | 时间与环境 | 设计目的 |
| --- | --- | --- |
| 第一次 | 暴雨前第3天，社会秩序正常，家庭尚不知道灾难规模 | 用220元预算和10格后备箱限制建立普通家庭采购选择 |
| 第二次 | 暴雨前第1天，降雨和预警升级，同时需要接家人 | 商店库存和价格开始变化，车辆路线、时间与接人顺序产生冲突 |
| 第三次 | 暴雨第1天，正式强降雨与红色预警出现 | 最后一次相对正式的采购，物资稀缺、限购或缺货，之后外出风险显著提高 |

其中“暴雨前第1天”的降雨属于灾难前兆；“暴雨第1天”代表持续百日的强降雨正式开始。

第一次购物商品包含主食、罐头、蔬菜、牛奶、巧克力、卫生用品、清洁用品、瓶装水、电池、充电宝和家庭常用药等。净水和更强的灾害用品可以在后续商店变化中出现，让玩家根据新信息重新判断，而不是开局就知道正确答案。

### 8.3 车辆与接人

- 汽车承担购物、接家人和部分外出探索。
- 暴雨前第1天，大孩子在学校，伴侣在社区，老人和小孩子已在家。
- 玩家选择先接伴侣或先接大孩子，并在安全主干道和排水河近路之间选择。
- 车辆受油量、道路积水、后备箱容量和时间影响。
- 接人分支在所有家人回家后重新合流，但顺序、路线、承诺和淋湿等状态继续产生后续反馈。

## 9. 核心系统需求

### 9.1 移动与互动

- 2.5D俯视角移动，使用键盘或手柄；后续为触摸操作预留输入层。
- 靠近人物或物体显示互动提示。
- 主要房间保持可行走、可理解的真实动线。
- 提供房屋快捷移动，减少已熟悉区域的重复走路；快捷移动不推进时间、不完成任务，外出场景中不可直接传回家。

### 9.2 对话与选择

- 家人对话通常提供2—4个选项。
- 关键选项原则上只能选择一次；重复对话显示与原选择对应的后续回应。
- 大部分对话选择产生轻微影响：信任标记、承诺、情绪、事件权重或后续台词。
- 只有少数关键选择改变资源、人物状态或事件路径。

### 9.3 物品、容器与携带

- 物品使用图标和格子显示，避免仅用文字列表。
- 冰箱、食品柜、卫生储物柜、后备箱和背包使用统一物品栏逻辑。
- 玩家随身背包当前为6格，汽车后备箱当前为10格。
- 大米、卫生纸、瓶装水等大件物资占2格，其余普通物品通常占1格。
- 容器之间允许取放；物品应自动回到合理储存位置。

### 9.4 家庭与生存状态

每名成员保留四项核心状态：

- 健康；
- 饱腹；
- 水分；
- 精神。

家庭共享资源包括食物份数、储备饮水、备用电力和常用物资。日常情况下系统自动进行合理分配；只有在严重短缺或人物冲突时，才让玩家决定优先顺序，避免每天重复分饭和上厕所。

### 9.5 供水与供电

供水状态：正常、水压偏低、水质异常、停水。

供电状态：正常、不稳定、停电。

- 正常供水时不消耗瓶装储备水；水质异常或停水时自动尝试使用储备水。
- 饮水不足降低水分状态，严重时损害健康。
- 停电影响照明、冰箱、充电、通信、收音机和家庭精神。
- 电池与充电宝转换为备用电力，但不能无限替代市电。

### 9.6 房屋状态

后续需要建立房间级标签，而不是给每个房间增加大量公开进度条：

- 正常；
- 潮湿；
- 漏水；
- 积水；
- 断电；
- 不可使用。

温度、霉变和卫生首先作为房间或家庭事件条件存在。只有测试证明玩家确实需要持续观察时，才升级为常驻公开数值。

### 9.7 外出探索

- 外出不是游戏主体，主要作用是补充物资、接触社区人物和承担风险。
- 外部世界控制在一条街和少量节点，不制作大地图漫游。
- 每次外出需要明确目的、预计耗时、携带限制和可能代价。
- 天气恶化后，外出频率下降、风险上升，住宅内部玩法的重要性增加。

### 9.8 每日结算

每天结算至少处理：

- 食物消耗；
- 饮水来源与消耗；
- 供水、供电变化；
- 五名成员状态变化；
- 房屋状态变化；
- 当天选择产生的延迟结果；
- 次日事件队列与提示。

结算只展示有意义的变化，普通生活行为由系统自动处理。

## 10. 事件系统

### 10.1 事件类型

| 类型 | 作用 | 示例 |
| --- | --- | --- |
| 固定主线事件 | 保证灾难阶段和核心剧情推进 | 正式暴雨、首次停电、一楼被淹 |
| 条件事件 | 根据资源、房间和历史决定触发 | 没有电池时无法听清广播 |
| 家庭成员事件 | 表现人物能力、弱点和信任 | 大孩子坚持查看社区消息 |
| 房间事件 | 让住宅状态进入画面 | 车库排水口倒灌、厕所返水 |
| 社区事件 | 展示外部世界变化 | 邻居求助、物资交换、道路封闭 |
| 外出事件 | 为探索提供风险与收益 | 接人路线积水、超市缺货 |

### 10.2 事件数据结构

每个事件至少包含：

- 稳定事件ID；
- 标题和事件类型；
- 可出现的日期或灾难阶段；
- 前置条件和排除条件；
- 提前线索；
- 发生地点；
- 参与人物；
- 选项；
- 即时结果；
- 延迟结果；
- 设置或清除的状态标签；
- 后续事件ID；
- 分支重新汇合的节点。

### 10.3 分支控制

- 主线按灾难阶段向前推进，不建立无限树状剧情。
- 选择主要通过隐藏标记、资源差异、人物信任和事件权重保留。
- 小分支在1—3个事件后重新汇合；重要选择可以在更晚阶段再次回调。
- 同一事件可以根据标签替换台词、选项或代价，而不是复制整条剧情。
- 只有人物死亡、住宅彻底失守和结局方向等极少数决定允许长期分裂。

### 10.4 示例：车库渗水

提前线索：灾前检查时发现车库地面较低、排水口有落叶；雨后能听见排水口异响。

事件发生：暴雨第3天，水从车库门缝和排水口进入。

可选应对：

1. 封堵门缝：消耗胶带或材料，短期降低进水，但可能掩盖水位继续上涨。
2. 用容器接水和排水：消耗行动时间，需要水桶，能延缓积水。
3. 优先转移物资：放弃控制水势，把工具和车辆物资移往高处。
4. 暂不处理：保留行动机会，但水位和损坏风险提高。

延迟结果：根据此前是否清理排水口、是否有工具、选择了什么行动，在次日改变车库状态、物资损坏和家人评价。事件随后回到共同的暴雨第4天主线，而不是生成四条永久剧情。

## 11. 首个纵向切片

### 11.1 内容边界

| 时间 | 可玩内容 | 主要验证目标 |
| --- | --- | --- |
| 暴雨前第3天 | 家庭需求、房屋检查、第一次普通购物 | 家庭介绍、价格、容量、房屋互动 |
| 暴雨前第2天 | 新闻、环境暗示和准备反馈 | 节奏、预测与伏笔 |
| 暴雨前第1天 | 降雨、接人、第二次购物 | 汽车、路线和选择回调 |
| 暴雨第1天 | 红色预警、最后购物、回家 | 商店变化与天气升级 |
| 暴雨第1夜 | 第一次正式家庭结算 | 食物、水和电力消耗 |
| 暴雨第2天 | 短暂停电 | 电池、充电宝和收音机反馈 |
| 暴雨第3天 | 车库渗水 | 房间事件、工具和物资转移 |

### 11.2 分支预算

1. 先接伴侣或先接大孩子。
2. 走安全主干道或排水河近路。
3. 车库渗水时封堵、排水、转移物资或不处理。
4. 电池、充电宝、饮用水、普通食品和此前承诺提供条件反馈。

所有普通分支在阶段节点重新汇合，不制作永久平行主线。

### 11.3 完成标准

- 玩家可以从开局连续游玩到暴雨第3天夜间，无阻断流程错误。
- 房屋主要房间均可正常通行，重要互动点容易发现。
- 三次购物在库存、信息和压力上有明显差别。
- 接人顺序和路线至少产生一次即时反馈和一次延迟反馈。
- 五名成员的状态能够被购物、天气、供水供电和事件改变。
- 玩家能在车库渗水前获得线索，并能理解不同应对方式的代价。
- 日期切换、保存读取、背包、容器、每日结算和事件状态能够完整保留。
- 调试工具可以快速跳到超市、购物后、当晚和第二天，降低重复测试成本。

## 13. 界面与可用性要求

- 顶部持续显示日期、时间、天气、地点和当前目标。
- 靠近可互动物时显示统一提示。
- 对话选项必须清楚显示，选择后提供相应反馈。
- 物品使用图标、名称、数量、容量和关键效果展示。
- 家庭状态界面同时展示五人状态和公共资源。
- 每日结算只列出当天真正发生变化的项目。
- 日期卡由玩家确认，不限制阅读时间。
- 调试按钮与正式游戏功能明确区分，并在发行构建中隐藏。
- 后续适配不同分辨率，并预留键鼠、手柄和触摸输入。

## 14. 美术与音频方向

### 14.1 美术

- 采用2.5D俯视角，空间维度参考俯视动作游戏，但节奏以探索和互动为主。
- 房屋比例首先服务通行和互动，真实感优先于严格建筑尺寸。
- 家具和房间采用模块化资源，少量关键物体拥有独立动画。
- 天气升级要能从窗外颜色、风、雨量、水面和室内光线直接看出。
- 一楼被淹应表现为持续变化过程，而不是突然切换一张背景图。

### 14.2 音频

- 雨声、风声、雷声和房屋异响是预测信息的一部分，不只是装饰。
- 不同楼层和房间需要不同的雨声遮挡与空间感。
- 停电、排水故障、收音机和车辆应有容易识别的声音提示。
- 背景音乐减少长时间高压，保留安静生活与突发事件之间的反差。

## 15. 技术与数据要求

- 主工程继续使用Godot 4.7 Standard和GDScript。
- 事件、物品、人物和房间尽量数据驱动，使用稳定ID与状态标签。
- 平台功能通过独立接口层处理，避免Steam、Web和微信逻辑写入核心规则。
- 存档必须保存日期、阶段、事件标记、家庭状态、房间状态、物资、车辆和玩家位置。
- 自动测试至少覆盖主要房间通路、购物、物品取放、生存结算、日期切换和关键事件状态。

## 16. 风险

| 风险 | 控制方式 |
| --- | --- |
| 100天剧情量过大 | 使用固定灾难阶段、事件模板、条件变体和重复地点变化，不要求每天完全独立 |
| 分支数量失控 | 小分支短期合流，用标签改变后续反馈而不是复制整条剧情 |
| 房屋探索变成重复走路 | 保留首次步行探索，提供不推进时间的快捷移动 |
| 系统过多导致日常繁琐 | 只保留健康、饱腹、水分、精神四项人物状态，其他生活行为自动结算 |
| 随机事件显得不公平 | 重大风险提前给线索，记录因果，随机性只改变条件和表现 |
| 微信适配拖累主工程 | Steam/Windows优先，微信端后期另做轻量版本 |
| 美术工作量过高 | 模块化房屋、模板化邻居住宅、程序占位图先验证玩法 |

## 17. 待确认问题

以下内容尚未正式定案，不应在开发中自行写死：

1. 五名角色的姓名、年龄、职业和最终能力数值。
2. 暴雨持续一百天的科学解释，以及是否需要明确解释。
3. 第100天的灾难结束方式和结局数量。
4. 中后期外出探索频率，以及玩家是否能够进入邻居住宅。
5. 温度、潮湿、卫生是否需要常驻数值，还是只作为状态标签和事件条件。
6. 家庭成员是否可能死亡、离家或永久失踪，以及这些结果从第几阶段开放。
7. 正式版是否保留房屋快捷移动，或将其包装为“选择房间行动”。
8. 最终美术风格、人物表现方式和是否使用角色立绘。
9. 开局具体季节，以及100天内是否进入冬季并启用低温压力。
10. Steam正式版的定价、试玩范围和发布时间。
