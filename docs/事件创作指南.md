# 《暴雨100天》事件创作指南

> 当前权威版本：2026-07-22。旧示例与旧人物关系全部作废。

## 一、事件的职责

事件用于把玩家已经能在房屋中观察、理解和干预的变化变成选择。它不负责代替基础机制，也不应每天早晨把全天内容一次性播报。

好的事件应做到：

- 有明确地点和可查看对象。
- 玩家可以通过此前观察预判风险。
- 不查看也是一种选择，世界不会等待玩家。
- 结果先有小变化，次日必须有至少一次清楚回应。
- 分支最后合流，避免每个选择永久复制主线。
- 夜间总结只说玩家知道的原事件和已经真实发生的后果。

## 二、必要字段

每个事件至少包含：

| 字段 | 作用 |
| --- | --- |
| `id` | 全局唯一ID |
| `title` | 玩家看到的标题 |
| `type` | 固定、房间、人物或外出 |
| `day` | 中文日期标签 |
| `phase` | 所属阶段 |
| `location` | HUD目标与日志使用的地点 |
| `interaction_id` | 地点事件绑定的物体或NPC，可选 |
| `conditions` | 日期、阶段、时间、标记与物品条件 |
| `text` | 玩家查看后才出现的正文 |
| `choices` | 至少一个可执行选项 |
| `effects` | 即时状态变化与延迟回响 |
| `merge` | 事件结束后的合流阶段 |

## 三、触发类型

### 晨间公共状态

只说明所有家庭成员都能立刻知道的内容，例如“外部电网中断”“水龙头仍出水但不可直饮”。不能在这里列出某扇窗漏水、某人藏了东西或某个房间设备坏了。

### 地点发现事件

通过 `interaction_id` 绑定到物体。玩家靠近后提示“查看：事件标题”，按E后才算发现。

### 人物事件

玩家靠近对应家庭成员后触发。真正需要玩家知道的强制信息，可让NPC主动走向玩家、在HUD目标中点名地点和人物，或设置截止时间后的主动提醒；不要假装所有人物事件都必须由玩家碰巧路过。

### 外出事件

从玄关进入独立事件场景，不依赖街道地图。第一个外出事件必须短、当天返回，并在次日用资源或状态变化完成小闭环。

## 四、选择结构

推荐每个事件2—3个选项：

1. 消耗已准备物品，得到确定结果。
2. 不消耗物品，承担风险或延迟后果。
3. 可选的折中方案，改变少量资源、时间或家庭状态。

不要用“正确答案/愚蠢答案”的写法。更好的取舍是把同一种资源放到不同用途，例如2卷胶带现在封窗，还是留给未来的容器和线路修补。

## 五、跨日回响

- `schedule_consequence`：适合不需要再次弹出完整剧情、只需在某日改变房间、设备、资源或人物状态的后果。
- `schedule_event`：适合次日需要再次查看、对话和选择的回访事件。
- 所有重要选择都应在次日有一个小回应。长期真相可以以后揭晓，但次日必须让玩家知道选择已被世界接住。

## 六、标准示例：窗沿渗水

```json
{
  "id": "r1_window_leak",
  "type": "room",
  "phase": "rain_day_1_free",
  "interaction_id": "window_living",
  "conditions": {"survival_day": 1, "min_clock": 450, "max_clock": 1380},
  "choices": [
    {
      "id": "seal",
      "conditions": {"required_item_amounts": {"duct_tape": 2}},
      "effects": [
        {"type": "consume_item", "item": "duct_tape", "amount": 2},
        {"type": "set_environment_state", "object": "window_living", "state": "sealed"}
      ]
    },
    {
      "id": "leave",
      "effects": [
        {"type": "schedule_consequence", "id": "living_window_leak_damage", "due_day": 2}
      ]
    }
  ],
  "merge": "rain_day_1_free"
}
```

未查看的隐藏规则由世界状态处理：事件本身不进第1天总结，但未封堵后果仍在第2天发生。

## 七、写入前检查

- 是否已经和用户确认具体剧情？
- 是否复用了现有地点、物品和角色，而不是凭空增加系统？
- 是否明确玩家如何发现它？
- 不查看时世界如何发展？
- 是否在次日给出回应？
- 是否有唯一ID、条件、结果和合流点？
- 新效果类型是否同步更新 `_apply_effect`、`_effects_summary` 和存档？
- 是否更新HUD目标和F1跳转入口？
- 是否避免恢复街道、车库和旧剧情人物？

未经用户确认，不先写具体剧情进JSON；可以先提出事件候选供讨论。
